# Macro `PLS_API` (2026-11-24, só forma)

Decisão do usuário (2026-11-24): trocar as chamadas
`pls::diagnostic::api_call([&]() -> decltype(auto) { return X; })` por `PLS_API(X)`.

```cpp
// src/kairo/common/diagnostic_profile.hpp
#define PLS_API(...) pls::diagnostic::api_call([&]() -> decltype(auto) { return __VA_ARGS__; })
```

A expansão é exatamente o texto substituído (sem `::` inicial, que mudaria os tokens).
Ferramenta: `tools/apply_pls_api.py` (só a forma exata: lambda cujo corpo é um único
`return EXPR;`; chamadas aninhadas de dentro para fora; tolera quebra de linha entre
`pls::diagnostic::` e `api_call(`), seguida de `tools/format_game_code.py`.

| `src/game/` | 10.145 em 140 arquivos | 0 |
| `src/kairo/common/generated/` | 252 em 33 arquivos | 0 |

Na primeira passada 7 chamadas ficaram de fora: estavam quebradas pelo clang-format
como `pls::diagnostic::` ↵ `api_call(` (a contagem por linha também as perdia: 10.138).
A expressão regular passou a aceitar espaço e quebra de linha ali; a contagem que

## O que depende da medição de `api_call`

Só o perfil do build de diagnóstico no PC: a separação do tempo de cada quadro em jogo
× plataforma (`PLS_FRAME_PROFILE`, lido por `tools/diagnostic_execution.py` e
`tools/summarize_execution.py`) e o tempo exclusivo por método (o tempo da plataforma
não é cobrado do método do jogo). Não dependem dela: o benchmark do New 3DS (o build ARM
não define `PLS_DIAGNOSTIC_BUILD`; lá `api_call` é a própria chamada), a cobertura dos
roteiros e a salvaguarda de métodos inalcançáveis (vêm de `PLS_METHOD_SCOPE`). A
remoção completa está proposta em `docs/backlog.md`, com a prova que exigiria.
